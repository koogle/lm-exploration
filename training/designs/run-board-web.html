Bench Runs

The training interface is now a web app served from the same Modal app that runs training. Its home screen answers two questions you couldn't answer before: how is every run doing, and what changed between any two of them.

Pick a baseline, read every run against it

Mark one run as A. Every row then shows its validation loss at equal tokens relative to A, and chips listing exactly what differs from A in code, config and data.

Compare any two runs

Mark another run as B. The panel on the right shows the result, a plain sentence on whether the difference can be pinned on one change, and the evidence: code diff, config keys, data mix, samples.

Honest attribution

When A and B differ in more than one thing, the panel says so and suggests a run that isolates one change. Try A = main, B = #16, then follow the suggestion.

Runs, numbers and samples are made-up examples. Loss is validation loss on TinyStories, compared at equal tokens seen. Click rows to set B, use the A/B buttons to choose both. iPad inference now has its own app and is not part of this screen.

What the training code has to record

Everything on this screen comes from two things: a recipe that describes what a run was asked to do, and metrics that describe what happened. The "what changed" chips are a diff of two recipes, so the recipe has to capture every input that matters.

  • recipe.json, written before step 0: git SHA, ref, resolved config, model hyperparameters, and the data mix with each source's path, weight and shard hash.
  • metrics.jsonl: step, tokens, train loss, val loss per source, tokens/s, learning rate, per-layer gradient norms.
  • samples.jsonl: fixed prompts, greedy, every 500 steps, so samples line up across runs.
  • Live values also go to a Modal Dict, since Volume writes only appear after a commit.

Bench Train

Three layouts for the Train phase. The app connects to one GitHub repo that holds the training code and the Modal pipeline. You never edit code in the app: you pick a branch or pull request, run it on Modal, and watch what training does.

branch / PR→commit SHA→Modal GPU clones it→metrics, logs, samples→GGUF checkpoint→run on iPad or Modal

All three use the Study C instrument look and keep the same top bar, with a Train / Inference switch. The repo, PRs, runs, losses and samples are made-up examples for the mockups. The model is a 13.8M-parameter Llama-style network (6 layers, width 384, vocab 8,192, context 256) trained on TinyStories. Tap PRs, runs and tabs: the mockups respond.

Study A

Run Board

Built to answer two questions: how is the current run doing, and how did a finished run perform and why. Pick a PR or branch on the left. The center shows what happened: a one-line verdict, the loss against the main baseline, and tabs for the exact model code at the run's commit, samples, gradients, logs and the diff. The right column shows what went in: the changes from main first, then the architecture, the data mix with every source traced to a Volume file, and the outputs.

How it explains a run

Every run is read against main. The verdict states the result, "Differs from main" lists the causes (code, data, config), and each cause opens its evidence: highlighted lines in the model code, the data mix, or the diff. Try #15 (data mix), #12 (code) and exp/high-lr (failure).

Good for

  • Seeing the exact code that ran, with lines that differ from main highlighted.
  • Knowing what data a run saw: sources, weights, tokens and epochs seen, shard hashes, and val loss per source.
  • Watching a live run: verdict, tiles, curve, logs and samples all update.

Costs

  • Comparing more than one PR against main means switching back and forth.
  • The verdict sentence has to be generated from metrics; it needs care to stay accurate.
Study B

Compare

Experiments are judged against each other, so the center becomes an overlay chart. Tick up to four runs on the left. The center plots validation loss against tokens seen, then lists only the config keys and files that differ. The right column puts generated samples from two runs side by side at the same step.

What you see

The answer to "should this PR merge?": how much lower the loss is at equal tokens, what changed to get there, and whether the text reads better.

Good for

  • Deciding between experiments, not watching one.
  • Fair comparison: the x-axis is tokens seen, so runs with different batch sizes line up.
  • Catching config drift: a run that differs in more than the PR claims shows extra keys.

Costs

  • Weak for live monitoring and debugging a single run.
  • No logs or gradient view; you'd need A or C next to it.
Study C

Pipeline

A run as a sequence of stages, like a CI job: clone the commit, load data, train, evaluate, export GGUF, ready. The current stage expands, logs stream underneath, and the right column browses the repo at that exact commit next to the Modal Volume, with a preview of the dataset as the model's tokenizer splits it.

What you see

Where a run is and what it ran on: the exact code, the exact data, and the files it produced. The last stage hands the checkpoint to the Inference phase, on the iPad or on Modal.

Good for

  • Trust and reproducibility. Every number traces to a commit and a dataset file.
  • Debugging failures that happen before training, such as clone, install or data.
  • Seeing the data, which the other studies hide.

Costs

  • The loss curve is reduced to a strip.
  • Feels like a CI dashboard; less insight into what the model is learning.

Recommendation

Build A as the Train screen, and fold the best parts of B and C into it as modes rather than separate screens.

  1. A is the default. Center: verdict, loss vs main, and tabs for model code, samples, gradients, logs and diff. Right: what differs from main, then Model, Data mix and Outputs.
  2. B becomes a "Compare" toggle on the chart. Ticking extra runs in the left list overlays them and swaps the Diff tab for the config-diff table.
  3. C's stage strip sits above the chart while a run is starting. Clone, data and compile take the first minute or two; once training starts it collapses into the header.
  4. C's full repo tree and token-level data preview open from the Model code and Data mix views when you need more than the model file and the mix.

What this asks of the backend

  • GitHub, read-only. List PRs and branches, read files and diffs at a SHA. A fine-grained token with read access to one repo is enough, since the app never writes.
  • A runner deployed from the repo. A Modal web endpoint with: start run (ref, config, GPU), list runs, stream metrics and logs, list checkpoints, download a file.
  • One Volume layout. datasets/… and runs/<id>/{metrics.jsonl, log.txt, samples.jsonl, ckpt/, model.gguf}. The app only reads it.
  • Training code that logs what the UI shows: loss, val loss per data source, tokens seen per source, tokens/s, learning rate, per-layer gradient norms, a sample every N steps, and the resolved config with each source's shard hash.

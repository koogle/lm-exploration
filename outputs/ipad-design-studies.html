Inference Bench

Three layouts for the v0 iPad app. Each one loads the local Qwen3.5-2B GGUF, chats with it on the left, shows the Metal source in the middle, and lists the model's layers on the right. They differ in how you inspect a forward pass while the model runs.

Gated DeltaNet mixer Full attention FFN (SwiGLU) Embedding / LM head Norms, residuals Sampling

The layer and tensor tables come from your GGUF file (names, shapes, quant types, byte sizes). The timings are a bandwidth model for illustration, not measurements. Every mockup is live: tap a token in the chat to load its forward pass, tap a layer or kernel to open its shader, press Run to replay generation.

Study A

Workbench

An Xcode-shaped tool in native iPadOS chrome. Chat lives in the sidebar, the shader editor takes the center with a collapsible forward-pass drawer below it, and an inspector on the right holds the model card and a layer tree you can expand down to individual tensors.

How inspection works

Pick a token, and the drawer shows that token's pass as one waterfall bar plus a table of kernels ranked by time, with achieved bandwidth. Expand a layer to see every dispatch with its tensor and quant type.

Good for

  • Fastest to build: NavigationSplitView, an .inspector, and a resizable drawer.
  • Most room for the editor once the drawer is collapsed.
  • Feels like a normal iPad app, which matters on a 11" screen.

Costs

  • Layer timing lives in a scrolling list, so you can't see the whole model at once.
  • Only one token at a time. Stalls that span many tokens stay hidden.
  • The drawer and the editor compete for the same vertical space.
Study B

Model Spine

The right column becomes the model itself: embedding, all 24 blocks, LM head, drawn as one row each with bar lengths set by time. While a token decodes, a highlight walks down the spine. The center opens on a kernel, with a header that says where the kernel runs and how close it gets to the memory-bandwidth limit.

How inspection works

The whole architecture fits on screen, so the shape of the cost is obvious: 18 DeltaNet blocks, 6 attention blocks, and an LM head bigger than any four blocks combined. Chat tokens are underlined by latency so slow ones stand out.

Good for

  • Learning the model while optimizing it. The 3:1 DeltaNet/attention rhythm is visible.
  • Kernel-first work: the header answers "is this kernel worth my time?" before you read any code.
  • Bandwidth framing fits decode, which is memory-bound.

Costs

  • The spine is a custom view that needs Canvas or a hand-tuned stack.
  • A wide right column leaves about 510 pt for code.
  • Still one token at a time; comparing tokens means tapping between them.
Study C

Token Scope

An instrument panel. Tokens appear as chips. The top of the center shows a CPU/GPU timeline for the selected token, gaps included. The right column is a heatmap of layers against tokens, so you see each layer's cost over the whole generation instead of one pass.

How inspection works

The timeline shows when the GPU sits idle while the CPU encodes. The heatmap separates two kinds of slowness: a uniform hot column is a system stall (clocks, thermals, a page fault), while a row that heats up over time is a kernel scaling with context, like attention.

Good for

  • Performance work across a whole generation, not a single pass.
  • Finding scheduling problems: CPU encode cost, command-buffer gaps, sync points.
  • Comparing a kernel edit against the previous run over many tokens.

Costs

  • Densest to build: timeline and heatmap both need Canvas and hit-testing.
  • The editor gets the least space of the three.
  • Hard to read until you know the model. Less useful on day one.

Recommendation

Build B in A's chrome for v0, and add C's timeline later as an optional strip above the editor.

  1. Shell from A. Native split view, chat in the sidebar, a standard toolbar with Load, Build, Profile, Run. It works with the keyboard, pointer, and Stage Manager without extra effort.
  2. Right column from B. The spine is the one view that teaches you the model and answers where the time goes. Tapping a row expands its dispatches inline, which covers A's tree.
  3. Center header from B. Calls per token, ms, share, and achieved GB/s against the iPad's peak. This is how you pick what to rewrite next. In the mock data it points to the LM head's Q6_K matvec.
  4. Later, from C. The CPU/GPU timeline once you start working on scheduling, and the heatmap once runs get long enough for stalls to matter.

Load stays simple in v0: one model card in the inspector with an Import button that opens the Files picker, then a progress list (header parsed, 320 tensors checked, file mapped, buffers created).

What the runtime needs to expose

  • A dispatch log per token. Each entry records layer, op, kernel, tensor, and bytes read. The UI draws only from this log, so every study runs on the same data.
  • Timing per layer. Apple GPUs sample timestamps at encoder boundaries, not per dispatch. A Profile toggle can split each layer into its own compute encoder and accept the overhead. Check supportsCounterSampling(.atDispatchBoundary) on the device.
  • Hot-swappable kernels. Your playground already compiles from source with makeLibrary(source:). Each kernel needs a CPU reference so Build can report max error before a new pipeline goes live.
  • Zero-copy weights. mmap the GGUF and wrap it with makeBuffer(bytesNoCopy:). Tensors become offsets into one buffer, which is what the layer list displays.
